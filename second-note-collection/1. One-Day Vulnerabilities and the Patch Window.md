# Note 1: One-Day Vulnerabilities and the Patch Window

**Quotation:** “In this work, we [Fang and his coauthors] focus on studying ‘one-day vulnerabilities,’ which are vulnerabilities that have been disclosed but not patched in a system. In many real-world deployments, security patches are not deployed right away, which leaves these deployments vulnerable to these one-day vulnerabilities” (Fang et al. 2024, sec. 2.3).

**Commentary:** I think the name “one-day” is misleading.
Going by the authors’ definition, a flaw stays a one-day vulnerability until the patch is actually installed, so how long it lasts depends on the organization running the software, not on the attacker.
Most of the sources I started with measure how fast attackers move, but this definition made me realize the length of the window is mostly up to the defender.
PHP2Shell is a good example.
The PHP Foundation released the fix on October 21, 2026, but it only covered the newest versions, and a lot of PHP runs inside other products, so many owners had to figure out whether they were even using PHP before they could patch (Ntsele 2026).
For them, the “one-day” window could easily have lasted weeks.
I’m going to use “patch window” as the main term in our project instead, since it puts the focus on the people who have to install the fix.
It also helps me explain what AI changes.
AI doesn’t create the window, it just helps attackers use more of it, which is what notes 2 and 3 get at.

**Subject terms:** one-day vulnerabilities; patch window; public disclosure; patch deployment
